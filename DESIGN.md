# Design notes

The assignment fixes the ISA, the assembly syntax and the command-line
interface. Everything below was left open: the object file format, how
relocations work, how wide values are encoded, and what the emulator does
where the specification is silent or contradicts itself. These are the
decisions made, the alternatives considered, and why.

## Assembler

### Parsing

The lexer and parser are generated by flex and bison (`misc/`). Directive names
and mnemonics are **not reserved words**. The lexer emits a plain identifier
for `section`, `word`, `halt` and everything else, and the parser decides what
it is. A keyword token per mnemonic would let bison do the dispatch. The cost
would be that no mnemonic could ever be used as a label or symbol name.

Numeric literals are decimal, hex, or octal with a leading `0`, as in C.

### One pass, then fixups at `.end`

The assembler reads the source once. Anything that depends on a symbol that
may not be defined yet is recorded and settled when `.end` is reached, in this
order:

1. **`.equ` symbols** are evaluated repeatedly until none make progress, so
   forward references and chains (`a = b + 4`, `b` defined later) work. If a
   round resolves nothing, the remaining symbols are reported as unresolvable
   or circular.
2. **Jumps** pick their final encoding (see below). This can add literal pool
   slots, so it must run before the pools are written.
3. **Literal pools** are appended to their sections, and the instructions that
   use them are patched.
4. **Relocations** are produced for every slot that still needs a symbol's
   final address.

### The 12-bit displacement and literal pools

An instruction has room for only a 12-bit signed displacement, so a full
32-bit constant or address can't be encoded in it directly. Such values go into
a **literal pool**: a list of 4-byte words appended to the end of the section.
The instruction then loads the value relative to `pc`:

```
ld $stack_top, %sp     →   92 ef 00 14     sp <= mem32[pc + 0x14]
```

There is one pool per section, and identical values share a slot. The
alternative is to emit pools periodically, jumping over each one, which is what
real ARM assemblers do. That handles arbitrarily large sections but adds a lot
of bookkeeping. One pool is enough for programs this size. If a section grows
past about 2 KB, the pool becomes unreachable, and that is a **hard error with
a clear message**, never silently wrong code.

### Jumps: pc-relative when possible

`jmp`, `call` and the branches have two forms: a direct one, where the target
is in the displacement, and a memory-indirect one, where the target is read
from memory. For a symbol target, the assembler emits the indirect form through
a pool slot by default. At `.end` it checks each jump. If the target is defined
in the same section and close enough, it flips one MOD bit and writes the
pc-relative displacement instead, and no pool slot or relocation is needed.
Jumps to other sections or files always go through the pool, because their
distance is only known after linking.

### One relocation type

Every relocation is `R_32`: write `S + A` into a 4-byte slot. The addend is
stored in the record (RELA style), and the slot itself stays zero. Which `S`
is used depends on where the symbol is defined:

- **Defined in this file:** relocate against its *section*, with the symbol's
  offset as the addend.
- **Not defined in this file:** relocate against the symbol itself, addend 0.

From the object file of `tests/relocatable/main.s`, where `stack_top` is
offset `0x80` in section `my_stack` (symbol 8), and `addTwo` (symbol 1) is
imported:

```
RELOC my_code 4
00000018 8 00000080      my_stack + 0x80   (stack_top)
00000020 1 00000000      addTwo + 0
```

This is the decision most of the linker builds on. Since no relocation ever
names a local label, the linker can throw local labels away, and a
`-relocatable` link never has to carry them into its output.

### `iret` is two instructions

The assignment summarises `iret` as `pop pc; pop status`. That order can't run:
the moment `pc` is restored, execution jumps away and the `status` restore
never happens. `status` can't simply be popped first either. Interrupt entry
pushes `status`, then `pc`, so `pc` is on top of the stack. So `iret` becomes:

```
96 0e 00 04    status <= mem32[sp + 4]                  (sp unchanged)
93 fe 00 08    pc <= mem32[sp];  sp <= sp + 8            (both words popped)
```

It is the only mnemonic that emits more than 4 bytes.

### `.equ` expressions

An `.equ` expression adds and subtracts symbols and literals. The legal
results are what one `R_32` relocation can express, so every term is treated
as *section base + offset*, and the section bases must either cancel out or
leave exactly one with coefficient +1:

- `end - start` (same section) → **absolute**.
- `start + 4` → **relative to start's section**.
- `start + end`, `2 * label`, or a difference across two sections → **error**.

GNU `as` produces the same three outcomes. `.extern` symbols are not allowed in
`.equ`. Supporting them would turn linker symbol resolution into a dependency
graph across files, with cycle detection (`a = b + 1` in one file,
`b = a + 1` in another).

## Shared between the tools

### The pc convention

Fetch, `pc += 4`, then execute. So a pc-relative displacement is measured from
the *next* instruction, and `call` pushes the address after itself. Getting
this off by 4 in either the assembler or the emulator would show up only as
programs misbehaving. So it lives in one place, `inc/isa.hpp`, as one constant
that the assembler's displacement calculation subtracts and the emulator's
fetch adds.

### File formats: one reader, one writer

The object file is plain text:

```
SYMTAB <n>
<index> <value> <type> <bind> <section> <name>      one per symbol
SECTION <name> <size>
<bytes as hex, 16 per row>
RELOC <section> <n>
<offset> <symbol index> <addend>                    one per relocation
```

`inc/objectfile.hpp` defines the format once, with a single reader and writer.
The assembler and linker each keep their own internal structures and convert
at the boundary. The assembler's pools and fixups are none of the linker's
business. The reader accepts both assembler output and `-relocatable` output,
and checks its input as it reads: a malformed file is reported with its line
number when it is loaded, not later when some value turns out to be wrong.

The memory image written by `-hex` and read by the emulator follows the same
pattern in `inc/hexfile.hpp`. It has rows of eight bytes, 8-digit addresses
(the assignment's example uses 4, but addresses go up to `0xFFFFFFFF`), and
only rows that contain data are written.

## Linker

### Merging and symbols

Sections with the same name are concatenated in command-line order. Each
file's part keeps its internal layout and just moves as a block.

- **Only globals are checked for multiple definitions.** An unexported label is
  private to its file, like `static` in C, so two files can each have their own
  `loop:`. The public tests depend on this: several files define a section
  named `isr`, and that section symbol must merge rather than clash.
- **An import is any symbol not defined in its file**, whatever its binding
  says. `.word foo` with no `.extern foo` still produces a relocation against
  `foo`, so the linker can't rely on the symbol being marked global.
- **An unused `.extern` is not an error.** "Undefined symbol" is reported only
  when a relocation actually needs the address, as GNU `ld` does.
- **Absolute symbols** (from `.equ`) resolve to their value, with no section
  base added. Level C of the public tests exports one across files.

### Placement

One running address does all of the layout. It starts after the highest end
address of any `-place`d section, or at 0 if nothing was placed. Every other
section goes there in merge order, packed with no padding. A `-place` naming a
section that no input defines is ignored, as in GNU `ld`. Any overlap is an
error that names both sections and their address ranges.

### Literal pools need no special handling

A pool is just bytes in a section, and the object format doesn't even mark
where it starts. An instruction and its pool slot are always in the same
file's part of a section, which moves as one block. So the pc-relative distance
between them survives merging unchanged.

Two things follow. Identical slots in different files are **not**
deduplicated: instructions point at specific slots, and shrinking a section
could push some other displacement out of range. And there is no padding
between files' parts, since nothing relies on pool slots being aligned.

### `-relocatable`

The output is a normal object file that can be linked again. Relocations are
rewritten rather than applied:

- A target that became defined by the merge is rewritten to point at the
  *merged section symbol*, with the addend adjusted. The output then uses only
  the same two kinds of relocation the assembler produces, so the reader needs
  no new case.
- A target that is still undefined is left alone. Only its offset moves.
- A relocation against an absolute symbol is already final, so its value is
  written into the bytes and the record is dropped.

Local labels are dropped, so a relinked object has fewer symbols than its
inputs. That is intended.

## Emulator

### Interrupts

On entry the processor pushes `status`, then the return address, and masks
interrupts globally. The assignment's pseudocode for `int` says
`status <= status & ~0x1`. Bit 0 is the timer mask, so that line would
*unmask* the timer on the way into the handler. This contradicts the general
rule stated elsewhere in the assignment, so the general rule was followed. It
is also the order `iret` is built against.

The return address pushed is always that of the *next* instruction. So after
a bad-instruction trap, `iret` resumes past the bad instruction instead of
trapping on it again forever.

### Arithmetic

Everything is unsigned except `bgt`, the one operation the assignment marks as
signed. So `div` is an unsigned divide and `shr` is a logical shift.

Division by zero traps as a bad instruction, since there is no value it could
produce. A shift by 32 or more yields 0, since there is an obvious answer,
even though C++ leaves that case undefined.

### Peripherals

- **`term_out`** prints the low byte of the word written to it. Level B of the
  public tests depends on this: it stores whole words loaded from a string and
  expects one character each.
- **Peripherals keep running while masked.** A keypress still lands in
  `term_in`, and the timer still counts. Masking only stops the processor from
  taking the request. Each device has one request bit, not a queue, so several
  requests made while masked become one.
- **`tim_cfg`** selects the period with its low three bits, since only eight
  periods exist. Writing it restarts the period. The next period is measured
  from when the last one ended, so a program that masked interrupts for a while
  doesn't get a burst of timer interrupts when it unmasks.
- When both devices are waiting, the **timer is served first**. The
  assignment doesn't rank them, but the order has to be fixed.
- The keyboard and the clock are checked **every 256 instructions**, not after
  every one. Both checks are system calls, and doing them per instruction made
  the emulator about 3× slower. A key is noticed at most 256 instructions late,
  roughly 40 µs. Requests that are already waiting are still taken at the very
  next instruction once interrupts are unmasked.

### Memory and reset

- Memory is allocated in 4 KB pages on first write. Unwritten memory reads as
  zero, and an all-zero word decodes as `halt`, so a jump into empty memory
  stops the program instead of running away.
- Instruction fetch reads plain memory and never the device registers, so a
  runaway `pc` can't execute `term_in`.
- Every register starts at zero, `status` included. So interrupts start out
  enabled, and a key pressed before the program sets `handler` sends the
  processor to address 0.

### The host terminal

For the duration of the run, the terminal is put in raw mode without echo, so
keys reach the program the moment they are pressed. stdin is also made
non-blocking, so the emulator keeps running when nobody types and when input
is piped. Ctrl+C is deliberately left working, because otherwise a program
stuck in a loop could not be stopped from the terminal it has taken over.

## Building on an old toolchain

The project had to build on the course's Ubuntu 20.04 machine (g++ 9.4,
bison 3.5.1, make 4.2.1), which is older than a typical development setup.
Three things mattered:

- g++ 9.4 supports C++17 fully but defaults to C++14, so every compile rule
  passes `-std=c++17`. A `static_assert` catches it if the flag is ever missing.
- `<filesystem>` compiles on g++ 9.4 but needs an extra library to link, so it
  isn't used.
- make 4.2.1 has no grouped targets (`a b &: dep`). It doesn't reject them
  either: they quietly turn into separate targets, which can run the recipe
  twice in a parallel build. The bison rule, whose single run produces both
  `parser.tab.c` and `parser.tab.h`, uses the older empty-recipe idiom instead.
